# A‑07. Запись контрольной точки при повторном входе в Weight

В предыдущем разборе при повторном открытии Weight между последней регистрацией света и следующим `LoadObject` прошло 33,528 мс. За это время был опубликован файл `AbandonedCampaign.v2.json`. У сохранённого тогда файла время создания и последней записи — 18:36:11.9467819 UTC, строка успешной публикации в журнале имеет метку 18:36:11.979 UTC. Разница составляет около 32 мс. Файловая метка относится к временному файлу, который становится слотом при замене; журнал имеет миллисекундную точность. Длительности отдельных системных вызовов именно в том кадре восстановить нельзя. [Трасса и фазы предыдущей версии](A07OpenLevel.md)

## Что мешало игровому потоку

На той же машине в сборке до изменения самый долгий новый вход дал 13,922 мс от последнего `AddLight` до начала завершающего кода камеры. Внутри этого интервала `SaveEntryCheckpoint` занял 13,921 мс. Проверены отдельные вызовы подготовки каталога, захвата блокировки, чтения предыдущего слота, сериализации, открытия, записи, сброса буферов, закрытия и публикации временного файла, очистки и освобождения блокировки. В этом входе 8,396 мс занял `IFileHandle::Flush(true)` (в Win64 вызывает `FlushFileBuffers`), ещё 4,686 мс — `MoveFileExW` с флагом `MOVEFILE_WRITE_THROUGH`. Открытие временного файла заняло 0,200 мс. [Вызовы Windows при публикации](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) · [Гарантии MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

Теперь при достижении камеры игровой поток под эксклюзивной блокировкой проверяет старую версию и архив, определяет следующий сегмент и сериализует JSON. Рабочий поток получает путь, текст и дескриптор этой блокировки. Он пишет отдельный временный файл в том же каталоге, полностью сбрасывает буферы, закрывает файл и заменяет слот с прежними флагами. Публикация считается успешной после замены. При ошибке прежний слот остаётся доступным, в игре появляется предупреждение. Проверки старого формата v1 через Unreal и обращения к игровым объектам выполняются в игровом потоке.

В процессе одновременно публикуется одна контрольная точка. Следующая операция чтения или изменения слота дожидается завершения уже начатой публикации. Состояние записи переживает выгрузку камеры. При штатном завершении игра дожидается записи и освобождает её объект результата до уничтожения пула событий UE. При принудительном завершении процесса во время записи на диске остаётся последняя успешно опубликованная версия. [Адаптер сохранения](../Source/Abandoned/Private/Infrastructure/Expedition/UnrealCheckpointStore.cpp)

## Сценарии и границы проверки

Две проверки на архиве кандидата принудительно удерживали замену существующего v2-файла средствами NTFS. Временный профиль содержал контрольную точку Stairs и запись архива `oxygen-restored`. Файловый oplock разрешал загрузить и проверить прежний JSON. Публикация Weight оставалась незавершённой до разрешения замены.

| Действие во время записи Weight | Длительность MoveFileExW | Где фактически ждали | Состояние после выхода |
| --- | ---: | --- | --- |
| Команда quit | 2027,411 мс | Игровой поток при штатном завершении, 548,898 мс | Код 0, Weight с исходным архивом |
| Сразу открыть Button | 2006,748 мс | Следующая запись на игровом потоке, 1602,443 мс | Код 0, Button с исходным архивом |

В обоих профилях успешная запись появилась в логе после снятия файлового барьера, временных файлов после выхода не осталось. В отдельной промежуточной сборке обнаружили остановку *после* закрытия журнала UE. Стек показал освобождение события последнего `TSharedFuture` при завершении CRT, после остановки пула UE. В финальной сборке это событие освобождается при штатном завершении работы движка; приёмка проверяет код реального игрового процесса. [Проверка двух незавершённых записей](../Scripts/Test-CheckpointPublication.py)

В полном Win64-пакете прошли `EntryCourse` (маршрут до станции), `EntryCheckpoint` (возобновление из Weight и сохранение Balance с архивом), `WorldLifetime`, `VulkanExitControl` и `VulkanTravelControl`. Все пять процессов завершились с кодом 0. Локальный отчёт — `Saved/UeVerification/20261119-190626-f551968b45f04a7984d230faa9910ccd/report.json`. Независимые C++20-тесты предметных правил и сценариев прошли в Debug и с `NDEBUG`, включая отрицательный контроль. Проверка совместимости со старыми слотами и отказов хранилища описана в руководстве по восстановлению прогресса. [Сохранения и контрольные точки](ProgressRecovery.md)

В том же пакете четыре исходных слота v1 мигрировали в v2 и загрузились повторно. При отказах первого сохранения и замены существующего слота прежние файлы сохранили SHA-256. Проверены неизвестная версия и запись пополнения кислорода. После последовательности Balance → Button → Stairs → Weight и немедленного штатного выхода новый процесс восстановил Weight с прежней записью архива. [Проверка миграции в пакете](Testing.md#миграция-сохранений)

## Воспроизведение

Стенд — Windows 11 x64 10.0.26300.10066, Core i5‑14400F, RTX 4070 Ti SUPER, драйвер 621.24, локальный том NTFS. Обе упакованные сборки используют UE 5.7.4, Vulkan SM6, 1920×1080, 100% масштаба, уровень теней 2, VSync и ограничитель частоты кадров выключены. В обеих применены патчи аудиомикшера и меток этапов LoadMap из #58. Первая сборка добавляет к #58 метки этапов записи и камеры. Во второй изменена публикация контрольной точки. Для каждого пакета последовательно запускали три независимых процесса на 4, 16 и 16 попаданий в Weight; новый пользовательский профиль в каждом. Первый OpenLevel выполнялся на кадре 500, затем каждые 550 кадров чередовались Stairs и Weight. Кэши Windows и драйвера между процессами сохранялись.

```powershell
foreach ($package in 'Saved/A07CheckpointBefore/Windows', 'Saved/A07CheckpointAfter/Windows') {
    foreach ($visits in 4, 16, 16) {
        $run = ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -WeightVisits $visits -TraceTravel
        python ./Scripts/Summarize-VulkanProfile.py $run
    }
}
```

В каждом `Travel.utrace` экспортируйте события всех потоков через консоль Timing Insights. Для каждого файла используйте свой каталог результата.

```text
TimingInsights.ExportTimingEvents C:/Captures/Events.csv -columns=ThreadName,TimerName,StartTime,EndTime,Depth -timers=Training_*,Checkpoint_*,UWorld::InitializeActorsForPlay
```
