# A‑07. Обход ссылок при переходе Stairs → Weight

## Почему затягивался обход

В двух соседних повторных входах из принятой сборки #59 сборщик обработал одинаковый граф: 1 967 ссылок из 424 объектов, кластеров — 0. В обоих случаях после обхода удалены 396 объектов из 839 просканированных слотов. В тринадцатом входе журнал отвёл обходу около 0,38 мс, в четырнадцатом метка `FRealtimeGC_PerformReachabilityAnalysis` заняла 11,106 мс. [Исходный набор переходов](Measurements/A07-TravelGC.csv)

На временной шкале проблемного входа десять задач `ExecuteForegroundTask` на рабочих потоках начались в первой десятой миллисекунды обхода и закончились вместе возле его правой границы. В UE 5.7.4 `ProcessAsync` распределяет контексты, отправляет задачи `CollectReferences`, обходит часть графа на игровом потоке и дожидается остановки всех контекстов. Длительность CPU-события включает периоды, когда задача не исполнялась на ядре. Архивная трасса позволяет сопоставить интервалы потоков. В двух отдельных прогонах канал UE Tasks связал 36 переходов с задачами `CollectReferences`. На предпоследнем входе в Weight во втором процессе обход занял 0,163 мс. На следующем — 11,833 мс. В длинном обходе все 13 задач начали исполняться за первые 0,089 мс, наибольшее ожидание в очереди составило 0,028 мс, а интервал от старта до завершения одной задачи — 11,785 мс. Пик возник уже после запуска задач, пока параллельный обход ожидал завершения общей работы. Разделить выполнение на ядре и вытеснение потока за этот интервал не удалось: для записи переключений контекста через WPR у текущей учётной записи не хватило прав. [Задачи по каждому переходу](Measurements/A07-ReachabilityTasks.csv)

## Изменение

[Патч CoreUObject](../Scripts/EnginePatches/UE-5.7.4-SmallFullGC.patch) выбирает встроенный последовательный обход для небольшой полной сборки. Проект задаёт `gc.SmallFullGCSerialSlots=1024`. Порог сравнивается с длиной диапазона слотов после постоянного пула, включая свободные позиции. Это верхняя оценка объёма работы по объектам. Порог выбран с небольшим запасом относительно 839 слотов при повторном входе в Weight. Число исходящих ссылок на объект может отличаться при развитии контента.

При превышении порога, инкрементальной маркировке и финальной очистке `GExitPurge` действует обычный выбор движка. Значение 0 отключает нововведение. Изменение затрагивает выбор обхода до распределения рабочих контекстов. Последующие сбор недостижимых объектов, ожидание рендера, освобождение памяти и проверка готовности объектов идут прежним путём. На проверенном маршруте сбор недостижимых объектов использовал девять потоков при обоих вариантах. [Применение патча и сборка](../CONTRIBUTING.md#обход-ссылок-в-небольших-камерах)

## Методика

Windows 11 x64 10.0.26300.10066, Intel Core i5‑14400F, RTX 4070 Ti SUPER, драйвер 621.24. Один Win64 Development пакет UE 5.7.4 с Vulkan SM6, 1920 × 1080, масштабом 100%, тенями 2, без VSync и ограничения частоты кадров. SHA‑256 исполняемого файла `b4005358aa8c3afb82014f5ffcc5aa7a9d1ddc492d570fe74cfd72643d13a6f0`.

Четыре процесса в порядке A1, B1, B2, A2. A отключает порог, B использует конфигурацию пакета. Каждый процесс получает новый профиль и 18 раз входит в Weight, с возвратом в Stairs между посещениями. Для повторных входов выборка содержит по 34 наблюдения в каждом варианте. В таблице CSV сохранены и первые входы. p95 берётся по ближайшему рангу вверх. Время кадра перехода — максимум 12 кадров начиная с команды открытия. [Все 72 входа](Measurements/A07-Reachability.csv)

Во всех 68 повторных входах обработаны 1 967 ссылок, 424 достижимых объекта и 396 удалённых объектов. Число контекстов обхода изменилось с 14 до 1. Медиана покамерных p95 времени кадра после стабилизации составила 5,487 и 5,493 мс соответственно. При дополнительном запуске с порогом в один слот все три перехода использовали параллельную ветвь. Анализатор отклонил трассу с последовательной ветвью при требовании `parallel`.

При максимальном кадре 24,413 мс (B1, пятый вход) полный GC занял 13,458 мс. В нём 0,214 мс пришлись на анализ достижимости, 5,623 мс на отложенное завершение объектов, 1,240 мс на `ShrinkUObjectHashTables` и 3,576 мс на `FMemory::Trim`. Это отдельные интервалы внутри GC. Следующая проверка — разделить стоимость очистки памяти и работы с хеш-таблицами на серии переходов, затем проверить влияние на кадр целиком. A‑07 остаётся открытым при бюджете 16,67 мс.

Сборка, cook и упаковка Win64 Development завершились с кодом 0. На полученном пакете прошли `EntryCourse`, `EntryCheckpoint`, `WorldLifetime`, `VulkanExitControl` и `VulkanTravelControl`. Проверки архитектуры и C++20 прошли в Debug и NDEBUG. Измерения относятся к указанной машине.

## Повторение

```powershell
$p = 'Saved/A07ReachPackage/Windows'
foreach ($control in $true, $false, $false, $true) {
    ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $p -WeightVisits 18 -TraceTravel -DisableSmallGCPolicy:$control
}
```

Для каждого запуска экспортируйте из Timing Insights события с колонками `ThreadName,TimerName,StartTime,EndTime,Depth` по списку для [полного GC](A07TravelGC.md#повторение), добавив таймеры `GC_ParallelReferenceTraversal` и `GC_SerialReferenceTraversal`. Скрипт сопоставляет журнал и трассу, затем сверяет фактическую ветвь при каждом переходе. Контроль A требует `parallel`, B — `serial`.

```powershell
python Scripts/Summarize-TravelGC.py "$run/Game.log" "$run/GC.csv" --expect-traversal serial
python Scripts/Summarize-VulkanProfile.py $run
```

Для разбора планировщика задач добавьте `-TraceTravelTasks` к отдельному контрольному прогону. В Timing Insights выберите задачи `CollectReferences`, запущенные между началом и концом `GC_ParallelReferenceTraversal` на игровом потоке. Для каждой доступны время постановки, начало исполнения и завершение. Этот подробный режим измеряется отдельно от сравнения производительности.
