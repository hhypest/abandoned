# A‑07. Повторный вход в Weight с авторскими FBX

21 ноября 2026 г. проверены два Win64 Development пакета UE 5.7.4. В первом были кубы и плита Meshy из PR #68, во втором — авторские DEV-01A, DEV-01B и DEV-02. Игровой EXE в обоих пакетах одинаков, SHA-256 `e722a7856208e0225f0fa5a9058969f3510e6f9ad6b272f8574fb39de6a44de7`. SHA-256 основного UCAS — `a8b045623e835b3eae491b2b1b30e51c14c48b24141cea01a6b0c8c16e0094b9` и `90862c7fdd148a8e2a146aadc5d29742683acc2076bccc04ed00d6dbf6843049` соответственно.

## Переход и память

Windows 11, Core i5-14400F, RTX 4070 Ti SUPER, 32 ГБ ОЗУ. Vulkan SM6, 1920 × 1080, Binned2, без VSync и ограничения кадров на время профилирования. Резерв MemStack выключен. Четыре обычных процесса в порядке FBX, Meshy, Meshy, FBX. Между первым и вторым процессами отдельно записана подробная трасса FBX. В каждом процессе восемь входов через Stairs. Первый вход исключён из времён повторного входа и включён в пик памяти всего процесса.

## Первый тик после LoadMap

В исторической трассе B3 из PR #68, вход 8, игровой поток провёл 10,768 мс в `WaitForTasks` внутри `TickCompletionEvents`. При повторном разборе рабочих потоков обнаружен интервал `Foreground Worker #1 → Tasks::Wait → Oversubscription → FWaitingQueue_CreateThread → CreateWorkerThread`. Создание потока началось через 0,265 мс после начала ожидания и завершилось за 0,178 мс до его конца. Оно заняло **10,325 мс**. В этой записи нет идентификатора задачи, связывающего оба интервала. [Исходная серия B3](A07WeightGC.md)

На авторских FBX в двух обычных процессах наибольшее ожидание внутри первого `UWorld_Tick` после загрузки составляло **0,464–1,041 мс** за 14 повторов. В отдельном процессе с `-TraceTravelTasks -TraceTravelStats` самый длинный участок ожидания на всех семи повторных входах находился внутри `TG_EndPhysics`, от 0,518 до 0,802 мс. На восьмом входе задача продвижения решателя Chaos (`FPhysicsSolverAdvanceTask`) выполнялась 0,670 мс. Связанная с ожиданием задача в графе стартовала через 0,123 мс после начала ожидания и завершилась за 0,008 мс до его конца. Интервал совпал с именованным CPU-событием решателя на рабочем потоке. Диагностический процесс исключён из сравнения пакетов.

Худший обычный кадр с FBX пришёлся на четвёртый вход второго процесса. Из 19,369 мс кадра 16,923 мс занял LoadMap. Внутри загрузки выгрузка мира заняла 0,805 мс, полный GC — 7,450 мс, инициализация акторов — 4,046 мс. Внутри GC на FMemory::Trim пришлось 2,870 мс. Уже после загрузки первый тик мира занял 1,471 мс, включая 1,005 мс ожидания задач.

## Как повторить

Для каждого пакета дважды запустить команду ниже в новом процессе. Для подробной трассы авторского пакета при третьем запуске добавить `-TraceTravelTasks -TraceTravelStats`. В Timing Insights найти `LoadMap_FullGC` при входе в Weight, затем первый `UWorld_Tick` после загрузки внутри того же `FEngineLoop::Tick`. Раскрыть `TickCompletionEvents → ProcessUntilTasksComplete → WaitForTasks` и посмотреть тот же интервал на рабочих потоках.

```powershell
./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -TraceTravel -WeightVisits 8
python Scripts/Summarize-VulkanProfile.py $run
```

A‑07 остаётся открытым. Бюджет кадра при 60 кадрах/с — 16,67 мс. Следующий замер — проверить вклад GC и инициализации акторов в кадры выше бюджета на большей серии и поймать редкое создание рабочего потока с записью зависимостей задач. Для проверки минимальной конфигурации требуется отдельный прогон с 8 ГБ ОЗУ и целевым GPU.
