# A‑07. Бюджет кадра при повторном входе в Weight

21 ноября 2026 года в упакованной игре на Vulkan измерен переход Stairs → Weight с авторскими моделями из PR #69. **Все 60 повторных входов превысили 16,67 мс.** Медиана кадра загрузки составила 17,856 мс, p95 — 19,869 мс, диапазон — 16,719–20,155 мс. Для p95 требуется выиграть 3,199 мс в полном кадре. [Измерения каждого входа](Measurements/A07-WeightFrameBudget.csv)

## Кадр и его фазы

В девяти из 60 повторов сам `LoadMap` превысил 16,67 мс. В остальных 51 загрузка уложилась в этот интервал, а полный кадр перешёл границу после учёта остальной работы. Для всех 60 повторов кадр с GC оказался самым длинным в окне перехода. Расхождение между длительностью кадра CSV и соответствующим `FEngineLoop::Tick` в трассе не превышало 0,004 мс.

Кадров в бюджете в выборке нет. Поэтому сравниваются 15 самых быстрых и 15 самых медленных кадров. В двух правых столбцах приведено среднее внутри группы, все времена указаны в миллисекундах. Вложенные строки входят во время родительской фазы.

| Интервал | Медиана по 60 | P95 по 60 | 15 быстрых | 15 медленных |
| --- | ---: | ---: | ---: | ---: |
| Кадр загрузки | 17,856 | 19,869 | 17,079 | 19,173 |
| LoadMap | 15,777 | 17,627 | 15,169 | 16,902 |
| Полный GC уходящего мира | 7,188 | 7,809 | 6,837 | 7,412 |
| ↳ Финальный FMemory::Trim | 2,451 | 2,900 | 2,204 | 2,612 |
| ↳ Финальный purge объектов | 2,482 | 3,123 | 2,517 | 2,406 |
| ↳↳ Отложенный FinishDestroy | 1,726 | 2,397 | 1,751 | 1,615 |
| Инициализация акторов Weight | 3,721 | 4,924 | 3,645 | 4,366 |
| ↳ Training_InitGame | 3,497 | 4,707 | 3,433 | 4,091 |
| Первый UWorld_Tick после загрузки | 1,056 | 1,393 | 0,976 | 1,264 |

Из разницы между группами в **2,094 мс** на GC приходится **0,575 мс**, на инициализацию акторов — **0,721 мс**, на другие операции внутри LoadMap — **0,437 мс**, на время кадра вне LoadMap — **0,361 мс**. Внутри GC наиболее заметно вырос финальный trim (+0,408 мс), а purge в медленной группе был в среднем на 0,111 мс короче. Внутри инициализации акторов почти вся прибавка пришлась на `Training_InitGame` (+0,658 мс). На игровом потоке сохранение контрольной точки дало разницу всего 0,013 мс. Это наблюдаемые различия между группами; результат изменения кода потребует отдельного A/B.

На входе, соответствующем p95 кадра (B2, посещение 3), из 19,869 мс на LoadMap ушло 17,627 мс. Внутри загрузки GC занял 7,303 мс, в том числе trim 2,896 мс и purge 2,404 мс. Время инициализации акторов составило 5,013 мс, из них 4,739 мс внутри InitGame. После загрузки первый тик мира занял ещё 1,086 мс. Все эти значения относятся к одному входу.

## Почему измеряли сборку комнаты

В D2 на каждом входе в Weight трасса зафиксировала 67 блоков без коллизии, 11 блоков с коллизией, четыре куба и одну плиту. Для 11 повторов получены следующие суммы по одному входу. Исходные времена и счётчики каждого входа есть в CSV.

| Фаза InitGame | Медиана, мс | P95, мс |
| --- | ---: | ---: |
| 67 декоративных блоков | 1,864 | 1,988 |
| 11 блоков с коллизией | 0,615 | 0,660 |
| Четыре физических куба | 0,242 | 0,272 |
| Напольная плита | 0,126 | 0,138 |
| Сохранение контрольной точки | 0,439 | 0,519 |
| Источники света | 0,069 | 0,082 |
| Весь Training_InitGame | 3,773 | 4,014 |

Каждый декоративный блок проходит через `Blockout::SpawnBox`: создаются отдельный AActor, UBoxComponent с профилем NoCollision и UStaticMeshComponent. Оба компонента регистрируются. Среди непосредственных вложенных таймеров декоративных блоков медианная сумма RegisterComponent составила 0,645 мс на вход, ConstructObject — 0,342 мс, SpawnActor — 0,294 мс. Все 67 деталей используют стандартный куб и четыре вида отделки (37 Frame, 16 Face, 8 Signal, 6 Mark). [Создание блоков](../Source/Abandoned/Private/World/Blockout.cpp) · [Раскладка камер](../Config/DefaultGame.ini)

## Предложение для согласования

**Проверить одним A/B-изменением отрисовку неподвижного декора Stairs и Weight экземплярами одного меша.** Область эксперимента — записи `Room` с `bCollision=False` в этих двух камерах. Один владелец на мир и компонент `UInstancedStaticMeshComponent` на фактическую комбинацию меша и материала заменят отдельные акторы и пустые коллизии декораций. Сохраняются исходные трансформы, отделка, параметры видимости и освещения. Блоки с коллизией, дверь, сигналы с изменяемым состоянием, кубы и плита используют существующую сборку.

Измеренные 1,864 мс — вся нынешняя стоимость сборки декора Weight. На этом участке остаётся цена создания и регистрации экземпляров. Возможный второй эффект — меньше объектов Stairs при следующем GC: у Stairs 59 неподвижных декоративных блоков. Влияние на trim и purge пока не измерено. По текущим данным экономию в 3,199 мс, необходимую для бюджета p95, обещать нельзя.

После одобрения сравнить режимы в одном EXE, чередуя процессы и набрав по 60 повторов на каждый режим. Основные критерии — p95 полного кадра (цель 16,67 мс), доля кадров в бюджете, время построения декора и фазы GC. Отдельно проверить кадры после перехода, пики RAM/VRAM, возврат из сохранения, коллизии, ход плиты и одинаковую читаемость сигналов на кадрах Stairs и Weight. Оптимизация ожидает решения владельца.

## Условия и воспроизведение

UE 5.7.4 Win64 Development, Windows 11 build 26300, Core i5-14400F, 32 ГБ ОЗУ, RTX 4070 Ti SUPER. План питания «Высокая производительность», Vulkan SM6, 1920 × 1080, масштаб 100%, тени 2, Binned2. VSync и ограничитель частоты выключены на время замера; резерв MemStack выключен. Для всех серий использовался один маршрут с возвратом из Weight в Stairs. На каждый процесс создавался новый профиль. Кэш ОС между процессами сохранялся.

- **B1–B4.** Четыре отдельных процесса по 16 входов. Первый вход каждого процесса оставлен в CSV и исключён из статистики, итого 4 × 15 повторов. Использован пакет PR #69, SHA-256 EXE начинается с `e722a7856208`, UCAS — с `90862c7fdd14`. Полные хеши указаны в [протоколе FBX](A07AuthorFBX.md).
- **D1.** Ещё один процесс на том же пакете, восемь входов с подробными именами таймеров UE. D1 служит контролем для интерпретации диагностических трасс.
- **D2.** Двенадцать входов с подробными именами на сборке с четырьмя дополнительными таймерами. Они покрывают создание блоков с коллизией, декораций, кубов и плит. Модели и конфигурация камер взяты из той же ревизии. У заново собранного пакета SHA-256 EXE `b83f4e685aeec4827278e8f703133c6b66c5ccb67d321eb97d7c25be4010849c`, UCAS `53e440e278eea9d2cf76027e5d10ca6e37c66f4b0ff45339f5b4889c90bcfd41`. Результаты D1 и D2 приведены в CSV отдельно от B1–B4.

```powershell
./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -TraceTravel -WeightVisits 16
# Для D1 и D2 добавить -TraceTravelStats и задать 8 и 12 посещений соответственно.
```

В Timing Insights экспортировать события GameThread из Travel.utrace с колонками ThreadName, TimerName, StartTime, EndTime, Depth. Включить короткие события и вложенные таймеры. Команда объединяет экспорт с журналом и покадровым CSV этого же процесса.

```powershell
python Scripts/Summarize-WeightBudget.py $run $events
```

Анализ связывает команду открытия Weight с единственным маркером GC в окне из 12 кадров CSV и находит игровой тик, содержащий полный GC и инициализацию акторов этого входа. Поле `ArrivalFrameMs` даёт длительность этого кадра из CSV, `WindowMaxMs` — максимум по всему окну. Медиана и p95 считаются по отдельным повторным входам. P95 соответствует 57-му из 60 значений по возрастанию.
