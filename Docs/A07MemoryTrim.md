# A‑07. Очистка памяти при переходе Stairs → Weight

В пакете Win64 Development на Vulkan замена Binned2 на Binned3 уменьшила время очистки памяти и увеличила паузу, которую видит игрок. Проект продолжает использовать Binned2. В обоих режимах UE выполнял полную сборку мусора с последовательным обходом и удалял 396 объектов при каждом повторном входе в Weight.

## Повторные входы

Четыре независимых процесса запускались в порядке Binned2, Binned3, Binned3, Binned2. В каждом использовался чистый профиль и 12 входов в Weight с возвратами в Stairs. После исключения первых входов в каждой группе осталось 22 наблюдения. p95 — 21-е значение из 22, отсортированных по возрастанию. Кадр перехода — максимум 12 кадров начиная с команды `open`. Интервалы GC вложены друг в друга. [Данные всех 48 входов](Measurements/A07-MemoryTrim.csv)

На сжатие хеш-таблиц пришлось 0,469 мс, на финальную очистку памяти — 3,879 мс, на отложенное завершение объектов — 6,225 мс.

Windows 11 x64, сборка 26300.10066, Core i5‑14400F, 32 ГБ ОЗУ, RTX 4070 Ti SUPER, драйвер 621.24. Для четырёх запусков взят один пакет UE 5.7.4 с исправлениями по #61. SHA‑256 исполняемого файла `b4005358aa8c3afb82014f5ffcc5aa7a9d1ddc492d570fe74cfd72643d13a6f0`. Vulkan SM6, 1920 × 1080, масштаб 100%, тени 2, VSync выключена, частота кадров свободная.

## Что входит в Trim

Разбор относится к финальному `FMemory::Trim` после `ShrinkUObjectHashTables` в том же `LoadMap_FullGC`. Ранее начатая инкрементальная сборка может завершить собственную очистку до обхода ссылок. Анализатор проверяет порядок и вложенность фаз каждого перехода.

В отдельной паре запусков со штатными подробными счётчиками UE медианы трёх повторных входов с Binned2 составили 1,600 мс для вызова обработчиков очистки и 1,040 мс для вызова аллокатора. С Binned3 те же интервалы заняли 1,522 и 0,283 мс. Оба аллокатора рассылают задачу сброса кешей потоков. В Binned2 после неё также освобождаются сохранённые страницы ОС.

Вторая диагностическая пара использовала пакет с четырьмя дополнительными метками CPU. В каждом процессе было по пять повторных входов в Weight. SHA‑256 этого исполняемого файла — `3a1ecf4fdf6c80a3adcd1c10d83f838dc04e68d48eda163e5d46bdaaf08b38cb`. [Все подробные замеры](Measurements/A07-MemoryTrimDetails.csv)

| Медиана, мс | Binned2 | Binned3 |
| --- | ---: | ---: |
| Вызов всех обработчиков очистки | 1,432 | 1,472 |
| Внутри него — освобождение страниц MemStack | 1,429 | 1,469 |
| Внутри него — очистка аллокаторов IoDispatcher | < 0,001 | < 0,001 |
| Освобождение кеша страниц ОС в Binned2, включая захват блокировки | 0,745 | В этом аллокаторе такой вызов отсутствует |

Основную часть времени обработчиков в обеих конфигурациях занял `FPageAllocator` из MemStack. Его обработчик извлекает свободные страницы по 64 КиБ из списка и возвращает их в кучу. В штатном Binned2 после сброса кешей потоков отдельно освобождается кеш страниц ОС. Пустая ячейка в CSV означает, что этот интервал отсутствует в данной конфигурации или режиме записи. Значения в наличии округлены до 0,001 мс.

Бюджет кадра перехода 16,67 мс остаётся открытым. Следующий опыт — сосчитать освобождаемые страницы MemStack и последующие запросы страниц при создании Weight. Это позволит проверить стоимость повторного наполнения пула до изменения правил освобождения памяти.

Диагностический пакет собран для Win64 Development с ранее приготовленным контентом. На Vulkan прошли EntryCourse, EntryCheckpoint, WorldLifetime, VulkanExitControl и VulkanTravelControl. Проверка архитектуры и тесты C++20 прошли в Debug и NDEBUG. Для старого экспорта без дополнительных меток обычный режим анализатора сохранил прежний результат.

## Как повторить

Из корня репозитория укажите путь к упакованной игре. Скрипт сверяет фактический аллокатор с журналом каждого процесса.

```powershell
foreach ($allocator in 'Binned2', 'Binned3', 'Binned3', 'Binned2') {
    ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -Allocator $allocator -TraceTravel -WeightVisits 12
}
```

Экспортируйте события из Timing Insights с колонками `ThreadName,TimerName,StartTime,EndTime,Depth`. К [таймерам #61](A07Reachability.md#повторение) добавьте `ShrinkUObjectHashTables,FMemory::Trim,FTaskGraphInterface_BroadcastSlow`. Интервалы игрового потока и кадры обрабатываются следующими командами.

```powershell
python Scripts/Summarize-TravelGC.py "$run/Game.log" "$run/GC.csv" --expect-traversal serial --memory-tail
python Scripts/Summarize-VulkanProfile.py $run
```

Для разбивки штатными счётчиками добавьте к запуску `-TraceTravelStats`, к экспорту — `STAT_FMemory_Trim_Broadcast,STAT_FMemory_Trim_GMalloc`, к анализатору — `--memory-tail stats` вместо `--memory-tail`. Для проверки отдельных обработчиков примените [диагностический патч UE 5.7.4](../Scripts/EnginePatches/UE-5.7.4-MemoryTrimScopes.patch) из корня исходников движка командой `git apply`, пересоберите пакет и снимите обычную трассу `-TraceTravel`. Добавьте к базовому экспорту `Memory_TrimDelegates,MemStack_TrimFreePages,IoDispatcher_TrimAllocators,Binned2_ReleaseCachedOSPages` и используйте `--memory-tail owners`. Подробные трассы обрабатываются отдельно от сравнения производительности.
