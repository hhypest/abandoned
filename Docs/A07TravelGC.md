# A‑07. Полная сборка мусора при Stairs → Weight

В типичном повторном переходе самая долгая фаза удаления — повторная проверка объектов, для которых асинхронная очистка ещё не завершилась. Медиана этой фазы составила **5,422 мс**. У самого длинного кадра причина внутри GC другая: обход ссылок занял **11,106 мс**, а отложенное завершение — **0,479 мс**. Это один и тот же переход во второй серии, четырнадцатый вход в Weight. Он дал 25,406 мс в `LoadMap` и 27,404 мс на кадр. [Исходные времена кадров](Measurements/A07-CheckpointFrames.csv) · [Фазы по каждому переходу](Measurements/A07-TravelGC.csv)

## Разбивка игрового потока

Повторно разобраны три трассы принятого пакета #59 — 4, 16 и 16 входов в Weight. В таблице только 33 повторных входа. Первое посещение в каждом процессе и обратные переходы в Stairs сохранены в CSV. p95 — значение с рангом `ceil(0,95 × N)`. Строки вложены: три последние входят в purge, а purge входит в полный GC.

| Интервал GameThread, мс | Медиана | p95 | Максимум |
| --- | ---: | ---: | ---: |
| Полный GC в LoadMap | 11,367 | 15,023 | 16,659 |
| Захват блокировки GC, сумма интервалов | 0,002 | 0,003 | 0,003 |
| Анализ достижимости | 0,313 | 9,682 | 11,106 |
| Финальный purge текущей сборки | 6,248 | 6,826 | 6,849 |
| Первый проход FinishDestroy | 0,529 | 0,733 | 0,770 |
| Отложенное завершение FinishDestroy | 5,422 | 6,012 | 6,023 |
| Удаление объектов после FinishDestroy | 0,230 | 0,300 | 0,368 |

`ConditionalFinishDestroyDeferred` включает повторные опросы готовности и вызовы завершения. Его длительность измеряет время на игровом потоке; отдельного таймера чистого ожидания GPU здесь нет. В проблемном входе полный GC занял 16,659 мс, из них 1,309 мс — purge. Дополнительно в этой же трассе виден `FMemory::Trim` длительностью 2,535 мс. Сам интервал анализа достижимости вложен в `CollectGarbageFull`; кто именно задержал исполнение внутри обхода, эта трасса не устанавливает.

## Очередь очистки и контрольный опыт

Собран отдельный Win64 Development с [диагностической меткой UE 5.7.4](../Scripts/EnginePatches/UE-5.7.4-DeferredGCTail.patch). По ключу `-TraceDeferredGCTail` движок записывает начальную длину очереди и последний объект, для которого проверка готовности вернула true. Время фиксируется до вывода строки. При пустой очереди такой строки нет. Объект определяется порядком обхода. Несколько объектов могут стать готовы одновременно.

20 ноября 2026 г. на RTX 4070 Ti SUPER, Core i5‑14400F, Windows 11, Vulkan SM6, 1920×1080 последовательно запущены три процесса одного и того же пакета. В каждом — новый профиль, восемь входов в Weight, без VSync и ограничения FPS. Для среднего процесса задано `r.OneFrameThreadLag=0`, что заставляет игровой поток синхронизироваться с предыдущим кадром рендера. Первый и третий процессы используют штатное значение 1. [Данные всех 24 входов](Measurements/A07-TravelGC-Control.csv)

| Медиана по семи повторным входам, мс | Штатно | С синхронизацией | Снова штатно |
| --- | ---: | ---: | ---: |
| Полный GC | 12,139 | 6,508 | 11,525 |
| Отложенное завершение | 6,190 | 0,102 | 5,645 |
| LoadMap | 21,002 | 16,110 | 20,343 |
| Самый длинный кадр в окне перехода | 22,954 | 35,110 | 22,198 |
| p95 кадра в установившейся камере | 5,559 | 5,949 | 5,083 |

В первом диагностическом процессе при каждом повторном входе отложены 273 объекта. Последним отмечен `GameplayDebuggerRenderingComponent`. Его базовый `UPrimitiveComponent` устанавливает `DetachFence` в `BeginDestroy` и проверяет этот барьер перед финальным удалением. В контрольном процессе тот же класс встречается и при ожидании меньше 0,1 мс. Порядок готовности компонентов сам по себе не обосновывает удаление игрового отладчика. Исходный код для сверки — `Engine/Source/Runtime/Engine/Private/Components/PrimitiveComponent.cpp` и `Engine/Source/Runtime/RenderCore/Private/RenderingThread.cpp`.

Синхронизация уменьшила измеряемую паузу внутри LoadMap, но ухудшила время кадра, которое видит игрок. В проекте оставлен штатный режим. Следующий опыт — снять планирование рабочих потоков на длинном проходе анализа достижимости и сравнить с обычным входом при том же числе объектов. Бюджет кадра 16,67 мс остаётся открытым.

## Повторение

Для разбивки времени достаточно пакета с метками LoadMap из #58. Для идентификации объектов примените диагностический патч к исходникам движка и пересоберите пакет. В каждом процессе посмотрите код выхода, маршрут, подтверждение Vulkan SM6 и отсутствие предупреждений об утечках. Это проверяет запускатель. Связь экспортированного CSV с журналом анализатор сверяет по порядку разгрузки/создания, камерам и времени инициализации акторов каждого входа. При незавершённой инкрементальной очистке до новой фазы маркировки отдельно выбирается финальный purge текущей сборки.

```powershell
$p = 'Saved/A07GCPackage/Windows'
$run = ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $p -TraceTravel -TraceDeferredGCTail -WeightVisits 8
# Для среднего процесса добавьте -DisableRenderThreadLag. Третий повторяет первый.
```

В Timing Insights для `Travel.utrace` экспортируйте события и выполните анализ.

```text
TimingInsights.ExportTimingEvents C:/Captures/GC.csv -columns=ThreadName,TimerName,StartTime,EndTime,Depth -timers=LoadMap_*,UWorld::InitializeActorsForPlay,AcquireGCLock,FRealtimeGC_PerformReachabilityAnalysis,IncrementalPurgeGarbage,ConditionalFinishDestroy,ConditionalFinishDestroyDeferred,DestroyObjects
```

```powershell
python ./Scripts/Summarize-TravelGC.py "$run/Game.log" C:/Captures/GC.csv
python ./Scripts/Summarize-VulkanProfile.py $run
```

В окне перехода берётся крупнейший из 12 кадров от команды открытия Weight, а в спокойной камере — p95 по кадрам 120–419 после команды. Колонки с начальной длиной очереди и именем класса пусты, если в журнале не было отложенного объекта. На диагностическом пакете прошли EntryCourse, WorldLifetime, VulkanExitControl и VulkanTravelControl. Графический профиль и правила освобождения ресурсов остались штатными.
