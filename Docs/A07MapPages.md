# A‑07. Свободные страницы MemStack при переходе Stairs → Weight

При штатной очистке пул освободил 131–136 страниц по 64 КиБ на повторный вход. Это 8,19–8,50 МиБ. Во время создания Weight из кучи потребовалось лишь 8–11 новых страниц. Наибольший спрос возник в первом полном тике после возврата из LoadMap.

Выбор аллокатора и исходные замеры очистки памяти приведены в [сравнении Binned2 и Binned3](A07MemoryTrim.md).

## Когда понадобились страницы

Диапазоны приведены по четырём повторным входам на вариант. Один запрос получает одну страницу. В штатном режиме у трёх входов вторая очистка не освободила ни одной страницы, в одном входе она освободила одну. Во всех восьми повторных входах между концом GC и началом предзагрузки новых запросов не зарегистрировано.

| Страницы по 64 КиБ | A · штатно | B · одна очистка перед возвратом |
| --- | ---: | ---: |
| Освобождены до предзагрузки нового мира | 131–136 | 0 |
| Получены из кучи при создании мира | 8–11 | 0 |
| Получены из пула при создании мира | 4–5 | 16–28 |
| Освобождены в конце LoadMap | 0 | 119–130 |
| Получены из кучи между возвратом и началом следующего тика | 3–7 | 5–11 |
| Получены из кучи за первый полный тик | 117–121 | 109–120 |
| Получены из кучи за следующие 11 тиков | 0 | 0 |

Основная часть страниц снова понадобилась уже после обеих проверенных точек очистки. Перенос на конец загрузки позволил обслужить создание мира из пула, но большая часть запросов первого полного кадра по-прежнему обратилась к куче. Во время последующих 11 тиков запросы продолжали обслуживаться из пула. [Счётчики по каждому посещению](Measurements/A07-MapPageCounts.csv)

На третьем входе CountA трасса первого полного тика содержит 117 обращений к куче. По ближайшему охватывающему CPU-событию на том же потоке 47 пришлись на `ParallelExecute (Async)`, 31 — на `FDeferredShadingSceneRenderer::UpdateLumenScene` и 15 — на `FRDGBuilder::ProcessAsyncSetupQueue`. Эти имена описывают работу рендера в одном кадре. Для воспроизведения выберите первый полный `FEngineLoop::Tick` после этого входа и раскройте родителей событий `MemStack_RequestHeap` на всех CPU-потоках.

## Цена для кадра

| Интервал, мс | A · медиана / p95 / макс. | B · медиана / p95 / макс. |
| --- | ---: | ---: |
| Полный GC | 11,590 / 12,926 / 12,955 | 10,337 / 11,129 / 11,319 |
| LoadMap по журналу движка | 20,472 / 23,313 / 55,503 | 19,064 / 21,383 / 21,859 |
| LoadMap до возврата, включая отложенную очистку | 20,508 / 23,343 / 55,537 | 20,741 / 22,885 / 23,866 |
| Наибольший кадр перехода | 22,203 / 25,498 / 57,722 | 22,881 / 24,739 / 26,110 |
| Наибольший кадр следующих 120 кадров | 6,111 / 6,990 / 8,107 | 6,122 / 6,890 / 7,009 |

В девятом входе A1 кадр занял 57,722 мс, полный LoadMap — 55,537 мс. Внутри выгрузки `LoadMap_AudioFlush` занял 38,92 мс, из которых 38,91 мс пришлись на `FTaskBase::TryRetractAndExecute`. Полная сборка мусора заняла 6,905 мс, а очистка MemStack внутри неё — 1,848 мс. Трасса локализует задержку на границе синхронизации аудио. Причину длительности самой задачи нужно установить отдельно. Это наблюдение включено в расчёт.

Диапазоны пиков рабочего набора процесса составили 1913–1956 МиБ в A и 1937–1946 МиБ в B. Частная память — 4108–4153 и 4128–4138 МиБ, выделенная VRAM — 2179–2181 и 2179–2179 МиБ соответственно.

В дополнительной паре A3/B3 медиана самого длинного кадра составила 22,616/23,323 мс, максимум — 23,873/26,110 мс. По всем 33 повторным входам на вариант p95 немного ниже в B, медиана выше. Сокращение медианы GC на 1,253 мс сопровождается отдельной очисткой в конце LoadMap длительностью 1,539 мс по медиане. Перенос оставлен диагностическим параметром. Проект использует штатную очистку.

A‑07 остаётся открытым при бюджете 16,67 мс. Следующий опыт — проверить ограниченный резерв до 128 страниц (8 МиБ) на время первого полного кадра. Оценивать нужно кадр перехода, следующие кадры, пик памяти и возврат резерва при выходе и нехватке памяти. Пик синхронизации аудио в A1 требует отдельной трассы задачи. Проверки кампании, контрольной точки, жизненного цикла мира, выхода и переходов на Vulkan прошли на диагностическом пакете со штатной очисткой. Каждый экспериментальный процесс также прошёл свой маршрут и штатно завершился. Тесты C++20 и архитектуры прошли в Debug и NDEBUG.

## Как измеряли

Испытан один Win64 Development пакет UE 5.7.4 с Vulkan SM6, Binned2, разрешением 1920 × 1080, масштабом 100%, тенями 2, без VSync и ограничения частоты. Машина — Windows 11 26300.10066, Core i5‑14400F, 32 ГБ ОЗУ, RTX 4070 Ti SUPER, драйвер 621.24. SHA‑256 игрового exe `d8371a761a4287df470b96487858a2b5a84f2434d15c0ff26b062cb60efb5339`. Диагностический пакет собран из исходников движка с ранее приготовленным контентом.

В режиме A MemStack очищает пул по каждому штатному вызову. В режиме B только обработчик MemStack внутри раннего `UEngine::TrimMemory` при смене мира откладывает очистку. После создания мира, перед возвратом из того же `LoadMap`, объект на стеке вызывает очистку один раз. Время этого вызова включено в `LoadMap_PageWindow`. Строка движка `LogLoad: Took …` записывается раньше. Остальные обработчики очистки, освобождение объектов и работа Binned2 выполняются в обычном порядке.

В шести процессах A1, B1, B2, A2, B3, A3 каждый раз создавался новый профиль. Каждый процесс 12 раз вошёл в Weight. Первые входы сохранены отдельно, по 33 повторных входа на вариант использованы для медианы, p95 и максимума. p95 — 32-е наблюдение в ряду из 33. Кадр перехода — наибольшее время кадра в окне из 12 кадров с команды открытия. Рабочий набор взят из счётчика пика Windows, private bytes и выделенная VRAM процесса по WDDM — по максимальной выборке каждого прогона. [Замеры кадров](Measurements/A07-MapPageTiming.csv) · [Память и идентификаторы прогонов](Measurements/A07-MapPageRuns.csv)

Подсчёт страниц выполнен в двух отдельных процессах, по пять входов в Weight. Событие запроса ставится при возврате из `FPageAllocator::Alloc` на вызвавшем потоке. Вложенный вызов `FMemory::Malloc` для 64 КиБ даёт метку `Heap`, получение страницы из пула — `Reuse`. При очистке считается число верхнеуровневых вызовов `FMemory::Free` внутри `TPageAllocator::Trim` на игровом потоке. Потоковые метки отделяют эти вызовы от других выделений и освобождений в процессе. Счётчики относятся к общему пулу и могут включать фоновую работу. Повторное получение страницы из пула показывает способ обслуживания запроса. Адреса страниц в этой записи отсутствуют. [Количество страниц по входам](Measurements/A07-MapPageCounts.csv)

Интервал `PostGC` длится от конца полного GC до начала предзагрузки. Интервал `Build` — от начала предзагрузки следующего мира до возврата из `LoadMap`. Остаток кадра до следующего тика обозначен `ReturnTail`, первый полный тик — `FirstTick`, период до завершения двенадцатого — `LaterTicks`. Число запросов в интервале равно сумме `Heap` и `Reuse`. Эти счётчики и время кадра измерялись в разных процессах.

## Повторение

Примените [диагностический патч](../Scripts/EnginePatches/UE-5.7.4-MapPageExperiment.patch) к исходному движку UE 5.7.4 с обычными патчами пакета из #61 и пересоберите игру. Для измерения времени используйте обычную трассу CPU.

```powershell
foreach ($defer in $false, $true, $true, $false, $true, $false) {
    ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -WeightVisits 12 -TraceTravel -DeferMapPageDrain:$defer
}
foreach ($defer in $false, $true) {
    ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package -WeightVisits 5 -TraceTravel -TraceMapPages -DeferMapPageDrain:$defer
}
```

Экспортируйте события всех CPU-потоков из Timing Insights. Для расчёта требуются полные окна каждого входа и 12 последующих тиков. Анализатор сверяет порядок камер и время инициализации акторов с журналом, а положение очисток — с режимом из `Run.json`.

```text
TimingInsights.ExportTimingEvents C:/Captures/Pages.csv -columns=ThreadName,TimerName,StartTime,EndTime,Depth -timers=LoadMap_PageWindow,LoadMap_FullGC,LoadMap_PreloadWorld,UWorld::InitializeActorsForPlay,FEngineLoop::Tick,MemStack_*,MemStackDrain/*
```

```powershell
python Scripts/Summarize-MapPages.py $run C:/Captures/Pages.csv
python Scripts/Summarize-VulkanProfile.py $run
```
