# A‑07. Пауза OpenLevel при Stairs → Weight

В исходном пакете #57 основную измеренную разницу между первым и повторным открытием Weight дал аудиомикшер. В одной трассе `LoadMap` вырос с 51,414 до 62,449 мс, а ожидание игрового потока перед GC — с 32,698 до 45,514 мс. Интервал GC от захвата блокировки до завершения обратных вызовов составил 5,330 и 5,177 мс, инициализация акторов — 7,875 и 6,980 мс. В других запусках повтор иногда быстрее первого. Задержка зависит от момента перехода относительно следующего аудиоблока. [Предыдущие замеры](A07Performance.md)

## Откуда взялось ожидание

При каждом обновлении слушателя `FAudioDevice::SetListener` передаёт в `FMixerDevice::OnListenerUpdated` упорядоченный список слушателей. Даже при неподвижной камере микшер каждый раз ставил копию тех же поз в очередь `SetListenerTransforms` аудиорендера. Для отдельного прогона #57 включили `au.debug.LogCmdQueueWhenReached 1`. Все 538 напечатанных первых команд в очереди оказались `SetListenerTransforms`; счётчик срабатывает при длине очереди один. После исправления тот же пробник напечатал три таких команды за весь маршрут.

При выгрузке `UEngine::LoadMap` вызывает `FAudioDevice::Flush`, чтобы снять ссылки на старый мир. Непустая очередь в `FMixerSourceManager::FlushCommandQueue` приводит к двум синхронизациям с аудиорендером. Обе видны в `LogAudioMixer Verbose`. На этой машине XAudio2 работает блоками 1024 отсчёта при 48 кГц (21,33 мс). Два диагностических вмешательства подтвердили происхождение паузы. С отключённым аудиоустройством первый/повторный `LoadMap` занял 27,154/23,022 мс. При включённом звуке и блоке 256 отсчётов две пары дали 29,773/24,431 и 25,352/33,345 мс.

Исправление сравнивает текущие позы с последним переданным массивом в аудиопотоке. Сопоставляются число и порядок слушателей, позиция, ориентация и масштаб с нулевым допуском. Изменившийся снимок отправляется прежним путём. Кэш сбрасывается при создании `FMixerSourceManager`. Устройство, размер блока, обработка плагинов, обновление скорости слушателя и штатный барьер выгрузки сохраняются. В отмеченной трассе исправленного пакета все три перехода пришли к штатному быстрому пути пустой очереди. [Патч микшера](../Scripts/EnginePatches/UE-5.7.4-ListenerUpdates.patch)

## Фазы перехода

Пакеты с включённой CPU-трассировкой дали следующие значения в мс. В исходном пакете аудиобарьер объясняет 24,412 мс из 26,018 мс прибавки при повторном входе. В исправленном на обоих входах он занимает менее 0,03 мс.

| Пакет и посещение Weight | Выгрузка | Аудио | GC | Создание | Остаток | LoadMap |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| До, первое | 1,100 | 25,249 | 5,493 | 9,198 | 1,424 | 42,464 |
| До, повторное | 1,063 | 49,661 | 5,383 | 11,310 | 1,065 | 68,482 |
| После, первое | 1,101 | 0,026 | 13,061 | 10,853 | 1,527 | 26,568 |
| После, повторное | 1,004 | 0,025 | 11,555 | 40,147 | 0,862 | 53,593 |

На повторе в трассе кандидата задержалась инициализация акторов. Внутри неё промежуток между регистрацией последнего `LightComponent0` и следующим `LoadObject` вырос с 3,862 до 33,528 мс. В этом промежутке игра синхронно сохраняет контрольную точку и сообщает о готовности Weight. Для атрибуции этой задержки файловой операции потребуется отдельная инструментированная проверка. Сам `BeginPlay` занял 0,307/0,326 мс. Полный GC в обоих захватах исправленной версии занял 11,4–13,9 мс против 5,4–5,5 мс в исходной. В каждой сборке purge обработал 400 объектов при первом открытии и 396 при повторном. Его длительность выросла с 0,870/0,806 до 8,313/4,771 мс, а на совпадающих контейнерах составила 8,919/6,577 мс. Поэтому сокращение полного LoadMap меньше снятого ожидания микшера. Причина изменения длительности purge требует отдельного замера.

`LoadMap` — длительность из `LogLoad: Took … seconds to LoadMap`. «Выгрузка» охватывает блок старого мира от уведомления об удалении уровня до снятия текущего мира за вычетом аудиобарьера. «Аудио» включает вызов `Flush` и сброс временной громкости. «GC» охватывает синхронный полный сбор в `UEngine::TrimMemory`, включая purge и обратные вызовы. «Создание» начинается с `PreloadContentForURL` и заканчивается возвратом из `UWorld::BeginPlay`. Остаток включает работу вне этих интервалов, в частности обслуживание рендера после GC, проверки и перерисовку. Пять столбцов складываются в полную паузу с погрешностью округления. [Метки движка](../Scripts/EnginePatches/UE-5.7.4-LoadMapScopes.patch)

## Серия без трассировки

Пять независимых запусков каждой сборки дали по десять открытий Weight. Порядок сборок чередовали попарно. Значения в таблице — медианы пяти запусков, мс. Окно из 15 кадров включает три кадра до команды и 12 начиная с её выдачи. Следующие 120 кадров проверены отдельно. [Все измерения и идентификаторы захватов](Measurements/A07-OpenLevel.csv)

| Показатель | До, первый | После, первый | До, повтор | После, повтор |
| --- | ---: | ---: | ---: | ---: |
| Полный LoadMap | 49,590 | 26,552 | 46,656 | 24,351 |
| Самый долгий кадр перехода | 51,474 | 28,679 | 48,667 | 28,309 |
| Сумма времени 15 кадров | 142,604 | 119,986 | 132,864 | 111,709 |
| Самый долгий кадр из следующих 120 | 6,579 | 6,432 | 5,941 | 6,414 |

Внутри одного процесса повтор оказался медленнее первого в двух парах до исправления и в одной после. В новой сборке максимумы за все пять процессов достигли 63,400 мс для первого LoadMap и 53,426 мс для повторного. В обоих случаях это был процесс № 2. Самый длинный кадр во всех окнах восстановления кандидата — 7,201 мс. На этой серии стоимость ожидания ушла из суммарного окна перехода, бюджет отдельного кадра в 16,67 мс пока превышен.

Максимумы процесса за пять запусков составили 1934,93/1919,10 МиБ working set и 2177,02/2177,01 МиБ выделенной VRAM до/после. WDDM опрашивался примерно раз в 100 мс. Каждый вариант использует отдельный пакет. Исходный — копия архива #57 с заново собранным Development EXE и метками; исправленный — новый архив UAT с теми же картами. SHA-256 исходного EXE — `EE8B13F3A3D4F68285C3A6DEB982D076ADB02A6F3A4634930710454DAD60065C`, исправленного — `6139207582E72FF068A264BCC354505906EF711BE3D1E90449ECFBD9636CCE38`.

Чтобы проверить влияние повторной упаковки, в копии исходного пакета заменили только EXE и его PDB файлами кандидата. Обе сборки в этом контроле использовали одни и те же физические файлы всех пяти контейнеров Pak/IoStore. Зафиксированы 27,260/24,482 мс без трассы и 27,898/23,436 мс с трассой. В последней паре аудиобарьер занял 0,027/0,028 мс. [Три пары с разбиением по фазам](Measurements/A07-OpenLevelPhases.csv)

В архиве кандидата прошли пять сценариев с кодом выхода 0. `EntryCourse` довёл игрока через четыре камеры к станции и пополнению кислорода, `WorldLifetime` проверил выгрузку миров после GC, `VulkanExitControl` и `VulkanTravelControl` — завершение пустого мира и повторных переходов, `VanguardFallsAudio` — декодирование вдоха в реальном микшере при падении. В логах пяти сценариев отсутствуют сообщения Vulkan об оставшихся выделениях и тайм-ауты аудиобарьера. Локальный отчёт — `Saved/UeVerification/20261119-183932-624072deb3064662ba858808dfb3dfa7/report.json`.

## Как повторить

Стенд — Windows 11 x64 10.0.26300.10066, Core i5‑14400F, RTX 4070 Ti SUPER, драйвер 621.24. Win64 Development, UE 5.7.4 из исходников, Vulkan SM6, 1920×1080, масштаб 100%, тени 2, VSync и ограничение FPS выключены. Каждый процесс начинает в Stairs с отдельным пользовательским каталогом. Команды CSV на кадрах 500, 1050 и 1600 открывают Weight, Stairs и Weight; после этого игра завершает захват на кадре 2200. Оба входа используют обычную абсолютную загрузку `/Engine/Maps/Entry` с параметром `Chamber`. Первый вход означает первый Weight в процессе; файловые кэши ОС и драйвера между запусками сохраняются.

Соберите два пакета из одного исходного состояния. В обеих сборках примените патч PartialDepth и патч меток LoadMap. Для второй сборки добавьте ListenerUpdates. Сохраните независимые каталоги пакетов. [Порядок сборки](../CONTRIBUTING.md)

```powershell
$before = 'Saved/A07MarkedPackage/Windows'
$after = 'Saved/A07OpenLevelPackage/Windows'
foreach ($n in 1..5) {
    $order = if ($n % 2) { $after, $before } else { $before, $after }
    foreach ($package in $order) {
        $run = ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $package
        python ./Scripts/Summarize-VulkanProfile.py $run
    }
}
$run = ./Scripts/Measure-VulkanPackage.ps1 -PackageRoot $after -TraceTravel
```

Повторите захват с `-TraceTravel` для исходного пакета. В Timing Insights откройте `Travel.utrace` из каждого каталога. Для экспорта нужны пять `LoadMap_*` и стандартный таймер инициализации акторов игрового потока. Укажите абсолютный путь назначения в консольной команде Insights.

```text
TimingInsights.ExportTimingEvents C:/Captures/GameThread.csv -columns=ThreadName,TimerName,StartTime,EndTime,Depth -threads=GameThread -timers=LoadMap_*,UWorld::InitializeActorsForPlay
```

```powershell
python ./Scripts/Summarize-OpenLevelTrace.py "$run/Game.log" C:/Captures/GameThread.csv
./Scripts/Invoke-UeVerification.ps1 -PackageRoot $after -Scenario EntryCourse,WorldLifetime,VulkanExitControl,VulkanTravelControl,VanguardFallsAudio
```
